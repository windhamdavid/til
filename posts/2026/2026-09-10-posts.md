Today I learned that I'll be swapping a new editor into the mix.

<!-- truncate -->

I watched *The Story of VSCode* this afternoon after it appeared front and center in my VSCode update notes. It's a story about Microsoft deciding that the way to win developers back was to give something away. It's really a story about **open source** — and it kinda misses the boat on crediting [Atom](https://en.wikipedia.org/wiki/Atom_(text_editor))[^2] and [Electron](https://en.wikipedia.org/wiki/Electron_(software_framework))[^3].

GitHub built Atom. To ship it as a desktop app they wrapped Chromium and Node into **Atom Shell** — first release July 2013, renamed **Electron** in April 2015. Atom itself went open source in May 2014. Both MIT. VS Code shipped as a desktop app on Electron. The runtime a competitor built for the editor it would eventually replace. Microsoft bought GitHub and announced Atom's end of life. So a company builds a runtime to ship its editor. A competitor builds on that runtime. The competitor's parent buys the company. The company's editor gets sunset, citing the competitor. And the competitor is still running on the runtime, today, on my machine, right now.

Nobody stole anything — that's what MIT *is*, and GitHub open sourced Electron precisely so people would build on it. And it is the *official* documentary which kinda reminds me of a board meeting with everyone patting themselves on the back for their own contribution. Nobody's lying. Everybody in there did do something. It's just that the version where you're the reason is the one that gets minuted, and the vendor whose work you're standing on doesn't have a seat at the table.

In early 2015 I ported the old TextMate Sunburst theme to Atom and published it — [atom-sunburst](https://davidwindham.com/code/atom-sunburst)[^4], MIT, two hundred lines of Less. Not an achievement. I bring it up for what's in the README: *an atom port of the TextMate Sunburst theme by Soryu*, with a link to his repo. I didn't agonize over that line. It's what you did. The other end of that decade is a VS Code extension — a little thing that highlights a word and drops in the Wikipedia link, which I ran at my desk for years and only [published](/posts/wikipedia-link)[^5] in 2024, when I started syncing to Codespaces and found it existed on exactly one machine. That one wasn't mine either. It started as an extension inspired by a fella named Arian Wasi in Bangladesh, which is the first thing I say about it in that post.


The link in my own [Atom notes](/docs/editors/atom)[^6] points at a registry that no longer exists, and the Sunburst I run in [VS Code](/docs/editors/vs)[^7] today is gerane's port, published days after Microsoft put the source on GitHub. Somebody else got there and theirs is the one that stuck which is the whole picture in miniature. The **Language Server Protocol**[^8] is the clearest case, and the one idea from this story I'd want someone to walk away with.

Before it, language support was a per-editor problem. If you wanted Python to work properly — completion, go-to-definition, the squiggle under a typo — somebody had to build Python support *for Vim*. Then again *for Sublime*. Then again *for Eclipse*. Ten editors and ten languages is a hundred separate integrations, most of which never existed. That's the real reason switching editors used to hurt. You weren't leaving the editor, you were leaving everything that made your language usable inside it. LSP breaks that in half. The language people write **one server**, which knows nothing about editors. The editor people write **one client**, which knows nothing about the language. A hundred integrations becomes twenty, and every new editor gets every language that already has a server, on day one, for free.

Note who's in the left-hand column. Eclipse. The IDE I bailed on gets Python and Go out of the same arrangement as everybody else, and so does Vim, which is forty years old. Nobody had to lose for that to work. And it rides on **JSON-RPC**, which is the same story one layer further down. JSON isn't Microsoft's and isn't anyone's. Crockford has always said he *discovered* it rather than invented it, wrote the spec down on a couple of pages, and put no committee in front of it. So the thing lying around free for the taking is what made LSP universal on arrival. That's three deep — a format nobody owns, carrying a protocol somebody gave away, running under a runtime a competitor built and open sourced. The editor is the thin part on top.

Which is why "VS Code is open source" does a lot of quiet work in that documentary. The VSCode repo is MIT. The build you download is not — Microsoft-licensed, telemetry, and a Marketplace restricted to official products. That's why VSCodium and Open VSX exist, and why every fork lands on a different extension registry than its users expect. The code is open; the ecosystem is the product. It's a fine business decision and I'd probably have made it too. But the interesting question is where that line got drawn, and it's the one the documentary doesn't ask.

Here's what I didn't expect, and the reason any of this is on my mind. I spend a good part of the day now talking rather than typing. I'm running a fleet of agents by voice. Not dictation. Speaking code into a buffer is a terrible idea — code is punctuation and exact names, and your mouth is bad at both. This is supervising. Several things run at once, I say what I want and what's wrong with what came back, and the typing happens somewhere else, by something else. That's really different job than my editor was built for. A text editor is a cursor in a buffer, and fifty years of refinement went into putting characters on a screen with the fewest movements — optimizing the thing that stopped being the bottleneck. My thirty colour overrides are in service of staring at one file. I'm not staring at one file. I'm watching four things happen and deciding which one has gone off the rails.

Nothing is really built for that yet and perhaps the reason for the doc. Zed has parallel agent threads and a toggle between putting the agent front and centre or the editor back where it was, which I read as a product being honest that nobody knows the answer. VS Code docks Claude Code in the panel — the same admission in a more conservative dialect. Both are text editors with a room added on. And it's the protocol thread again, one layer up. LSP made the editor a thin client over language servers. MCP and ACP are making it a thin client over agents. The editor keeps getting thinner, and the part that matters keeps moving out of it into something that speaks a protocol.

Nathan Sobo, who worked on Atom, announced [Zed](https://zed.dev)[^9] in 2022 as the spiritual successor. Written in Rust. No Electron. Read after the chain above, that isn't a product decision, it's a rematch. I'm not entirely sold, and I'm not switching. I'm adding it to the mix — which is what I did with Cursor for a while, until SpaceX bought it[^10]. That's the sort of thing that decides these questions for you now, and it's a strange sentence to have to write about a text editor.

My own reason for looking is pretty boring. The [Ralph](/docs/ai/ralph)[^11] setup runs through VS Code's agent mode against local models, and the friction is in my [models](/docs/ai/ralph/models)[^12] notes: it refuses agent mode under a 64K context window and offers no setting, so the fix gets baked into a Modelfile. Then you deselect its built-in tools by hand, or the model spends its budget on the editor's idea of a tool instead of the thirteen I built for it. Both are plain settings in Zed — `context_window` in a JSON file, and a saved agent profile instead of checkboxes that reset. It speaks MCP, so the tools come with me. I wrote the rest up at [Editors → Zed](/docs/editors/zed)[^13].

I've moved editors before — Eclipse to TextMate to Sublime to Atom to VS Code — always because the new one was faster or the old one stopped being maintained. Eclipse set the pattern. It was a Java IDE carrying the full weight of a Java IDE: workspaces, perspectives, a build system with opinions about my life, a splash screen I could go get coffee during, all so I could edit a stylesheet. It was built for a different job than the one I had. TextMate opened instantly and got out of the way, and that was the whole argument. Which makes the loop funny. The man who led the Java tooling on the IDE I ran away from is the man who built the editor I eventually ran to. By my count Erich Gamma has made me switch editors twice — once by building something far too heavy for the work, and once by building something light enough to end the argument for a decade. This might be the first time I moved for a reason that has nothing to do with editing text so why even call it a text editor.
