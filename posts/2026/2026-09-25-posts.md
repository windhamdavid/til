Today I learned how to more easily hand a whole project back and forth between machines without losing anything in the middle.

<!-- truncate -->

The obvious reason to keep a second machine working is that the first one might not. But [ovid](/docs/computers/ovid)[^1] travels, and [stu](/docs/computers/stu)[^2] doesn't, so the backup case is the boring half. I try to build my git remotes in a way to that the environment can be replicated. Being somewhere else and picking up exactly where I left off — same sites running locally, same notes, same database. The parts move by different means on purpose and the goal is being system agnostic.

This workflow configuration change was inspired by a recent server migration in which I figured out that I can always keep a local linux copy ( [cotton](/docs/computers/cotton)[^3] ) running up under my desk to orchestrate future server migrations and I wanted to have a similar setup migrating between development machines. 

And also... I'm headed down to the beach in a week and I really enjoy just popping into the next virtual meeting with the ocean in the background without all the preemptive emails and autoresponders about 'vacation time'. Clients usually let me lay low once they know while I'm still available if needed and I take pride in my 24/7 'on call' service even though I might be away from my desk. 

## ssh & git

The two Macs reach each other over plain SSH on the LAN — mDNS names, not addresses, because the laptop takes an ordinary DHCP lease and roams. No port forward, so this works at home only, which is the intended limit. It's essentially the same as my work with any server so the hop from development machine to production is essentially the same.

Each machine holds its own key for the other. Not a copy of one shared key: a per-machine key means a lost laptop is one line out of an `authorized_keys` file, with the desktop's access untouched. The config blocks that name those keys live in the `_servers` repo, one file per direction, and get appended to `~/.ssh/config` by hand — so the block is documented even when the machine it belongs on is asleep.

A non-default key filename fails in a way that reads like the wrong thing entirely. The laptop's key matches none of the names SSH walks on its own, so without a `Host` block the key is never offered and you land on a password prompt. From a GUI session the agent already holds the key and it all works, which hides the problem until the first time you `git fetch` from inside an SSH session. Once SSH is up, git does the state. Anything with real remotes — the theme repos — just pushes and pulls. The repos with no remote, like `_servers` and the site root, sync straight across the LAN:

```sh
git remote add ovid ovid:Sites/whatever    # one time
git fetch ovid && git merge ovid/main
```

Pull-based, from whichever machine wants the work. Nothing gets pushed into a checked-out branch.

## local/remote

Mostly because of AI agents, I've started using the root of each project to store skills, memory and project info. I've also started using a local git repo on the entire project instead of just the app or site. I keep all of the agent files versioned, and it ignores everything by default and re-admits only what belongs — the markdown, the scripts, the audits, the `.example` files. The  `.env` and other config files can generally match up by just commenting out the other machines the same as I've always done between production, staging, and development environments. 

That's the layer I didn't expect to matter as much as it does. Code that arrives without its notes arrives without the reasons. Everything I worked out about a project — why a script filters what it filters, which thing bit last time — travels in the same commit as the change it explains, to whichever machine I'm sitting at.

## project specs

There are some per-project specifics, which are mostly the databases. Each project gets one file describing its own move with a written procedure and two scripts to move it.

The databases travel as files rewritten on the way out. The export script infers direction from the site's own 'home' option, so the same command does the right thing on either box — run on the desktop it writes the laptop's dump, and vice versa. It rewrites URLs in two passes that are protocol-relative and JSON-escaped. And it rewrites collations in the file just in case I needed to move it to another database server. An import replaces the database wholesale. There's no merge, so whichever box was edited last is the one that has to send, and the other must not have edits waiting.

Everything left is host-specific by design and stays put — the hosts entry, the local cert, the vhost. Uploads and images go by `rsync` when there are new ones. Each of those is a line in the sync file rather than something I try to remember. Three layers, three mechanisms, and the split is the thing I'd keep: git for what's authored, a written script for what's generated, and per-host files that never move at all.


## system agnostic

I'm not big fan of the whole pull down and setup an entire development environment ( aka - Docker ) for each project given that I generally use only a couple of my preferred tech stacks between projects and machines. Don't get me wrong... for a public project where the environment is often mis-replicated and the tickets fill up from configuration issues - it makes sense.

I've spent a lot of time recently rigging up [ralph](/docs/ai/ralph)[^4] primarily so that I can also be agent agnostic so it makes sense that I'd have my entire workflow machine agnostic too. And I suppose that in an ideal development workflow, the developers themselves are swappable too. 

The amount of time I've spent over the years configuring machines makes me think I should have just been using this type of setup all along. You don't know what you don't know until you know it, but I feel like some senior neck beard coulda cued me into this years ago.  And just like my [cotton](/docs/computers/cotton)[^3] config for remote servers, I'm just going to start treating my development workstations as swappable and interchangeable using brewfiles with one parent repo to manage them where every new step introduces some workflow improvements.
